Multi-tenant SaaS template

ForgeSaaS Handbook

Everything needed to run this template locally, understand what is inside it, turn it into your own product, and deploy it. Written for someone who has not seen the codebase before.

The repository has no README — this document is the entry point. Where a topic has a deeper operational guide, it points at the file rather than repeating it, because a copy in two places is a copy that will be wrong in three months.

What this is

A production-shaped, multi-tenant SaaS application that you fork and turn into a product — not a starter kit you read once and outgrow.

"Multi-tenant" means one running application serves many customer organisations, and every piece of data belongs to exactly one of them. That single idea shapes most of the codebase: every tenant-owned table carries an org_id, and one repository layer applies that filter so no individual query has to remember to.

What is already built and tested:

  • Accounts and organisations — sign-up, email verification, invitations, roles (owner / admin / member), an organisation switcher.
  • Authentication — passwords (Argon2), TOTP two-factor, WebAuthn security keys, Google/GitHub sign-in, magic links, and optional per-organisation enterprise SSO.
  • Billing — Stripe checkout, the customer portal, webhooks, plans, subscriptions, dunning, and optional usage metering.
  • The surrounding machinery — file uploads with virus scanning, in-app/email/push notifications, feature flags, an audit trail, GDPR export and deletion, an admin console, a public API with scoped keys, and outbound webhooks.
  • Four front ends — a React web app, an Expo mobile app, an Astro marketing site, and transactional email templates.

Nearly all of it is optional. Fourteen features are modules you switch on or off with one boolean each, and "off" means the routes return 404 and the database tables are never created — not that a button is hidden. That mechanism is the heart of the template, and it has its own section.

The one file to read first

TEMPLATE.md is the contract between the template and your product: which files the template owns and will overwrite, and which are yours forever. Reading it before you customise anything saves you a painful merge later.

Setting up

  1. Install dependencies

    shell
    corepack enable
pnpm install

cd backend
python -m venv .venv
# Windows: .venv\Scripts\activate    macOS/Linux: source .venv/bin/activate
pip install -e ".[dev]"
cd ..

    A virtual environment under backend/.venv is worth creating even if you normally skip them: several scripts look there first when they need an interpreter with the backend installed.

  2. Create your environment file

    shell
    cp backend/.env.example backend/.env

    The example file has working local defaults for everything except third-party keys. You need a Stripe test key only when you touch billing, and email lands in Mailhog locally, so you do not need a mail provider to start.

  3. Start everything

    shell
    make dev

    That single target does five things in order:

    1. Builds the email-template CLI (the worker shells out to it, so it must exist on the host first).
    2. Brings up the Docker stack.
    3. Waits for the backend to answer /health.
    4. Runs database migrations.
    5. Seeds a starter organisation, plans and a superadmin.

  4. Open it

    https://localhost — the web app. Your browser will warn once about the certificate: Caddy issues itself a local one, which is correct and expected. Accept it.

    https://marketing.localhost — the marketing site, once you have run pnpm build. It is a separate host, and you may need 127.0.0.1 marketing.localhost in your hosts file for it to resolve.

If the backend never becomes ready

Run docker compose logs backend. The usual cause is a missing or malformed backend/.env — the application refuses to start rather than run with an invalid configuration, and the log line names the field.

Repository layout

A pnpm workspace with a Python backend beside it. Shared code lives in packages/ so the four front ends cannot drift apart.

backend/ # FastAPI application app/ core/ # config, database, cache, security, module loader models/ # shared table mixins modules/ # one directory per feature — the unit of on/off auth/ tenancy/ billing/ storage/ notifications/ admin/ audit/ gdpr/ api_keys/ webhooks/ sso/ feature_flags/ product_settings/ _template/ middleware/ # security headers, rate limits, maintenance mode workers/ # background jobs (arq) and the scheduler alembic/versions/ # migrations, one directory per module branch tests/ # ~2,300 tests against real Postgres and Redis product/config.py # YOUR module toggles + branding apps/ web/ # React SPA — the product itself marketing/ # Astro static site — the public pages mobile/ # Expo / React Native app packages/ api-client/ # typed client, generated from the OpenAPI schema ui/ # component library + design tokens hooks/ utils/ # shared React hooks and helpers i18n/ # translations, one JSON namespace per area types/ validation/ # shared types and Zod schemas email-templates/ # transactional emails, rendered by a small CLI docs/ adr/ # architecture decision records — the "why" runbooks/ # operational procedures — the "how, when it breaks" product.config.ts # YOUR module toggles + branding (frontend) TEMPLATE.md # the template/product contract

Two directories deserve emphasis. docs/adr/ records why a decision was made and what would change it — read one before arguing with the design. docs/runbooks/ holds procedures for when something needs doing or has gone wrong; there are twenty-plus, and they are the most useful thing in the repository when you are on call.

The stack, explained

Every technology here, what it does, and why it was chosen over the obvious alternative. If a name is unfamiliar, this section is written for you.

Backend

Web framework

FastAPI

Handles incoming HTTP requests and routes them to Python functions.

Why: it derives the API documentation and request validation from ordinary Python type hints, so the schema cannot drift from the code. That generated schema is also what produces the typed frontend client.
Database toolkit

SQLModel & SQLAlchemy

Define tables as Python classes and query them without writing SQL by hand.

Why: SQLModel makes one class serve as both the database table and the validation model. SQLAlchemy underneath is the mature engine that makes the hard queries possible when you need them.
Database

PostgreSQL + asyncpg

The database itself, with a driver that does not block while waiting on it.

Why: Postgres has the JSON support, full-text search and transactional guarantees this needs. "Async" matters because one server process can then serve many requests while queries are in flight.
Schema changes

Alembic

Version control for the database schema — every change is a reviewable file.

Why: each optional module keeps its migrations on its own branch, so a module you never enable never creates its tables at all. That is what makes "off means gone" true.
Background jobs

arq + APScheduler

Work that happens outside a request: sending email, scanning uploads, delivering webhooks.

Why: a user should not wait for an email to send. arq runs queued jobs on Redis; APScheduler handles recurring ones like pruning old records.
Cache & queue

Redis

Fast in-memory storage for caches, rate-limit counters and the job queue.

Why: one dependency covers three needs. Cache keys are centralised in one file so an invalidation is never forgotten.
Passwords

Argon2

The algorithm that turns a password into something safe to store.

Why: it is deliberately expensive in memory as well as time, which is what makes stolen hashes impractical to crack. It won the competition held to find exactly this.
Tokens

joserfc & python-jose

Signing and verifying the tokens that prove who a request is from.

Why: sessions are RS256-signed JWTs — signed with a private key, verifiable with a public one. joserfc is the maintained library used for verifying identity-provider tokens in enterprise SSO.

Web front end

UI

React + Vite

The component model, and the build tool that serves it instantly while you edit.

Why: the largest ecosystem and hiring pool. Vite over older bundlers because a reload takes milliseconds, not seconds.
Routing & data

TanStack Router + Query

Router maps URLs to screens; Query fetches, caches and refreshes server data.

Why: the router is fully type-safe — a typo in a link is a build error. Query removes almost all hand-written loading and caching logic.
Generated client

@forge/api-client

A typed function for every API endpoint, generated from the backend's schema.

Why: rename a field in Python and the frontend stops compiling. It is generated offline with every module switched on, so the types exist whatever your product enables.
Forms & validation

react-hook-form + Zod

Form state, with validation rules shared between frontend and backend.

Why: the rules live once in @forge/validation, so the browser and the server cannot disagree about what a valid email is.

Marketing site & mobile

Marketing

Astro

Builds the public pages to plain HTML with no JavaScript unless a component needs it.

Why: marketing pages are judged on load speed and search ranking. Astro ships zero JS by default and lets one interactive piece — the pricing toggle — become an "island" of React on an otherwise static page. See docs/adr/0004.
Mobile

Expo / React Native

One codebase producing real iOS and Android apps.

Why: it reuses the same API client, validation and translations as the web app. Expo removes most of the native build toolchain pain.
Styling

Tailwind CSS

Styling written as utility classes in the markup.

Why: design tokens live in @forge/ui and both the app and the marketing site consume them, so a brand change happens once.
Translation

i18next + ICU

Text in six locales, including right-to-left Arabic.

Why: retrofitting translation is expensive; starting with it is nearly free. Note that placeholders use ICU syntax — {name}, single braces.

Infrastructure & operations

Edge

Caddy

The web server in front of everything: TLS, security headers, static files.

Why: it obtains and renews HTTPS certificates automatically, including locally. The marketing site is served as a second host from a generated config block.
Connection pooling

pgbouncer

Sits between the app and Postgres, reusing a small pool of connections.

Why: Postgres connections are expensive and finite. In production only — see docs/adr/0002 for the trade-offs it brings.
Observability

Prometheus, Grafana, Sentry, OpenTelemetry

Metrics, dashboards, error reports and request traces.

Why: when something is slow or broken in production, you need numbers rather than guesses. All four are wired up and off by default locally.
Services

Stripe, Resend, ClamAV

Payments, transactional email, virus scanning for uploads.

Why: each is replaceable behind an interface. Email has a local backend so development never sends anything real.

The module system

The central idea. Fourteen features, each one boolean. Off means the routes 404, the tables are never created and the UI is absent — not that something is hidden behind a flag.

Toggles live in two files that must agree: backend/product/config.py and product.config.ts. Both belong to your product and are never overwritten by a template update.

backend/product/config.py
MODULES = EnabledModules(
    billing=ModuleConfig(enabled=True),
    notifications=ModuleConfig(enabled=True),
    public_api=ModuleConfig(enabled=True),      # turn one on
    enterprise_sso=ModuleConfig(enabled=False),
)
ModuleDefaultRequiresWhat it is
billingon—Stripe checkout, portal, webhooks, plans and subscriptions.
notificationsonbillingIn-app, email and push notifications with per-user preferences.
file_storageonbillingUploads to S3/MinIO, with virus scanning.
feature_flagson—Per-organisation flags and their admin toggles.
gdpron—Data export, consent records, self-serve deletion.
adminon—The internal admin console and its API.
oauthon—Google and GitHub sign-in, account linking.
totp_2faon—Authenticator-app two-factor and step-up prompts.
multi_orgon—The organisation switcher. Off pins each user to one org.
marketingon—The Astro site and the Caddy block that serves it.
usage_meteringoffbillingUsage records and metered pricing.
outbound_webhooksoffbillingCustomer-facing webhooks with retries, replay and a delivery log.
public_apioff—Org-scoped API keys with scopes and per-key rate limits.

Dependencies are enforced, not documented

The Requires column is declared by the template, not by your config. Enabling enterprise_sso with oauth off raises a RuntimeError at boot naming both modules. A half-configured stack fails loudly at start rather than quietly at the first request.

Turning one on

shell
make migrate-plan   # shows which module branches will be applied
make migrate        # creates that module's tables
make dev            # restart

docs/runbooks/module-toggle-guide.md walks through each toggle in both directions, including the ones with consequences worth knowing before you flip them twice.

Turning one off keeps the data

Disabling a module does not drop its tables — your customers' rows survive so the switch is reversible. Two cases deserve care: an API key stops authenticating the moment public_api goes off even though its row remains, and disabling enterprise_sso un-enforces SSO for every organisation at once, which matters if those users have no password.

The matrix that keeps it honest

CI runs the whole suite in three configurations: the shipped defaults, every optional module off, and the Phase 4 modules on. This is not ceremony — the first time it ran it found 86 failures, two of which were real defects that only appear when a module is enabled. If you add a code path that queries something only when a module is on, that job is what will catch the test file you forgot.

Tenancy & auth model

Two rules explain most of the backend. Understanding them prevents the two most expensive classes of bug in a multi-tenant product.

Rule one: org_id is sacred

Every tenant-owned table carries an org_id, and BaseRepository applies that filter to everything it builds. You do not write the filter per query — you inherit it. A dedicated test sweep probes every org-scoped endpoint from the wrong organisation and fails the build if any of them answers.

The database is shared, with row-level separation. docs/adr/0007 explains why that was chosen over a schema per tenant, names PostgreSQL row-level security as the next step if stronger assurance is ever required, and lists the five measurable thresholds that would reopen the question.

Rule two: there are two kinds of caller

A session is a person: a short-lived signed token plus a refresh token in a cookie. An API key is a program: a long-lived credential with explicit scopes and its own rate limit. Both arrive on the same Authorization header and are told apart by prefix.

The important asymmetry: an endpoint accepts a key only if it explicitly declares a scope. Every other endpoint refuses one, including everything under /api/v1/api-keys — a key that could mint another key would be a privilege-escalation primitive.

What a user can be

  • Roles — owner, admin, member, per organisation. A user can hold different roles in different organisations.
  • Superadmin — a platform-level flag for the admin console, requiring two-factor.
  • Impersonation — support staff can act as a user, with every destructive action blocked and the whole session audited. A CI sweep requires every mutating route to either carry the guard or an explicit written exemption.

The loop when you add an endpoint

  1. Write the route, schema and repository method in backend/app/modules/<module>/.
  2. Write the test. The suite uses a real database, so tests describe real behaviour.
  3. make gen-client — the frontend now has a typed function for it.
  4. Use it in apps/web. A wrong field name is a compile error, not a runtime surprise.
  5. make lint && make test.
If a just-generated symbol "does not exist"

The generated client is gitignored and built on demand, and the build cache has been known to serve a stale copy. Run make gen-client then pnpm build before believing the error.

Making your own product

The template is designed to be forked once and then kept up to date for years. That only works if both sides respect one boundary.

The contract

Your product owns these files. A template update never touches them:

  • product.config.py and product.config.ts — toggles and branding
  • .env.product.example — your own environment variables
  • apps/web/src/routes/_product/ — your own screens
  • backend/app/modules/<your-module>/ — your own features
  • CHANGELOG.product.md and README.md
  • apps/web/src/features/support/SupportWidget.tsx, if you wire up a support tool

Everything else belongs to the template and will be overwritten. If you must change a template file, record why in CHANGELOG.product.md so the next merge conflict has an explanation attached.

Starting a product

  1. Fork, and keep the template as a remote

    shell
    git clone <your-fork> my-product
cd my-product
git remote add upstream <forgesaas-template-url>
git fetch upstream

    Without the second remote you cannot pull improvements later — do it now, not when you need it.

  2. Choose your modules

    Edit backend/product/config.py and product.config.ts together. Turning things off is as valuable as turning them on: less surface to secure, fewer tables, a smaller app.

  3. Claim a migration prefix

    Migrations are numbered so template and product changes never collide. The template owns 0001–0099; your product takes 0100–0199. Record it in the table in TEMPLATE.md, and put your migrations under backend/alembic/versions/product/.

  4. Brand it

    Product name, colours and support details come from the two config files, and design tokens live in packages/ui. Changing them once updates the app, the marketing site and the emails.

  5. Build your first feature

    make new-module NAME=invoices, then see the next section.

Pulling template updates

shell
make check-template-drift          # what has landed upstream since you forked
make update-from-template          # fetch + merge
# resolve conflicts, taking the template version unless you have a written reason
make dev && make test              # verify before pushing
Merge a tag, not a branch

Always merge a released tag (upstream/vX.Y.Z) rather than upstream/main. A tag is a state someone verified; main is whatever landed an hour ago.

Adding a module

A module is a directory with a fixed shape. The generator writes the shape and tells you what it cannot do for you.

shell
make new-module NAME=invoices

That creates backend/app/modules/invoices/ containing:

FileResponsibility
models.pyDatabase tables. Tenant-owned ones carry org_id.
schemas.pyRequest and response shapes. Never expose a model directly.
repository.pyThe only layer allowed to build queries. Org scoping lives here.
service.pyBusiness logic. Does not commit — the router owns the transaction.
router.pyHTTP endpoints, permissions and rate limits.
README.mdWhy this module exists and what to know before editing it.

The generator prints the manual follow-ups with file and line pointers. They are:

  1. Add the toggle to EnabledModules and both product config files.
  2. Register the router conditionally in build_router().
  3. Add the Alembic branch and its tables to the migration map, then write the first migration.
  4. Add the module's routes to the surface map so the toggle matrix tests it.
Two rules the build enforces

Every list endpoint needs an entry in the query-budget suite — a missing one fails the build, which is how N+1 queries are caught before review. And every mutating route needs either the impersonation guard or a written # impersonation-ok: reason.

Rehearse it locally first

This boots the production compose file — the only stack that routes through pgbouncer — migrates, checks readiness and inspects the connection pool. It overwrites backend/.env; restore yours afterwards.

Configuration that differs in production

The application refuses to boot outside development without TLS on DATABASE_URL and REDIS_URL and a PASSWORD_PEPPER set. This is deliberate: a .env that works locally is not one that works in production, and the failure is at startup rather than at the first request.

Deploying to your own server

A worked example, start to finish: one VPS running the whole stack behind Caddy, on a domain with Cloudflare DNS. This was written by doing it, so the traps in it are real ones rather than anticipated ones. Roughly €5–8 a month.

Pick an x86 server, not ARM

CI builds linux/amd64 only — a plain docker build, no buildx and no --platform. ARM instances are around half the price and tempting, and the image will not run on them. Adding multi-arch to the build job is a small change if you want that saving; make it before you provision.

4 GB of RAM is enough provided the frontend is built somewhere else — in CI, or in a container as below. The running stack is about 900 MB (Postgres, pgbouncer, Redis, MinIO, backend, worker, Caddy); it is pnpm build that is memory-hungry, not serving.

  1. Point three DNS records at the box

    Three hosts, because the app and the marketing site are separate origins and object storage needs a public one of its own. Keep them DNS-only (grey cloud in Cloudflare) for the first deploy: Caddy needs a clear path to Let's Encrypt, and a proxy in front changes both the challenge and the client IP handling.

    RecordServesSet by
    @The marketing siteMARKETING_DOMAIN
    appThe SPA and the API, one originDOMAIN
    storageMinIO, proxied by CaddySTORAGE_DOMAIN

    All three must resolve before the stack first starts. Caddy orders a certificate per hostname at boot and backs off on failure, so a missing record costs minutes of unavailability rather than a clean error.

    The SPA and API sharing one origin is deliberate: no CORS, and the __Host-refresh_token cookie needs no special handling. Splitting them across two registrable domains breaks the session in a way that only shows up on the second token refresh.

  2. Prepare the machine

    shell — as root
    apt update && apt upgrade -y && apt install -y make git
curl -fsSL https://get.docker.com | sh

adduser --disabled-password --gecos "" forge
usermod -aG docker forge
mkdir -p /home/forge/.ssh && cp ~/.ssh/authorized_keys /home/forge/.ssh/
chown -R forge:forge /home/forge/.ssh && chmod 700 /home/forge/.ssh

# swap: cloud images ship with none, and the frontend build OOMs without it
fallocate -l 2G /swapfile && chmod 600 /swapfile
mkswap /swapfile && swapon /swapfile
echo '/swapfile none swap sw 0 0' >> /etc/fstab

    Open only 22, 80 and 443 inbound. Nothing else is published: the backend, Postgres, Redis and MinIO are reachable only on the compose network. That is what makes TRUSTED_PROXY_IPS and METRICS_BLOCKED_AT_EDGE truthful rather than aspirational.

    Everything from here runs as forge, never root.

  3. Clone

    shell
    ssh-keygen -t ed25519 -f ~/.ssh/id_ed25519 -N "" -C "forge-prod-deploy"
ssh-keyscan github.com >> ~/.ssh/known_hosts 2>/dev/null
cat ~/.ssh/id_ed25519.pub   # add as a read-only Deploy key on the repo

git clone git@github.com:YOU/YOUR-REPO.git ~/forge && cd ~/forge

  4. Edit the one committed setting

    PRODUCTION_ORIGIN in apps/marketing/src/config/indexing.ts ships as https://example.com. It is committed source, not configuration, because indexing is opt-in — a fresh clone tells crawlers nothing until somebody states where production is. Change it to your apex and push, then pull on the box.

  5. Generate the configuration

    Run this on the server so the secrets are created where they will be used and never travel. Replace the three hostnames.

    That last file is not a duplicate

    .env at the repo root is Compose's own environment, and the only place it reads ${...} from. backend/.env is handed to containers as env_file: and is never consulted for interpolation, so a variable a compose file expands has to be in the root file or it silently becomes its default.

    What it buys: docker-compose.prod.yml gives the caddy service STORAGE_DOMAIN as a network alias, so the backend and worker resolve the storage hostname to a container. They have to use the public name — there is one AWS_ENDPOINT_URL and the presigned URLs built from it go to a browser — so without the alias every server-side S3 call leaves the machine, crosses whatever CDN or WAF fronts the domain, and comes back. When that was Cloudflare, its bot protection answered 403 to roughly 7 % of them, and the only symptom was uploads failing at the confirm step with a stack trace pointing at HeadObject.

    The backend and worker refuse to start when this hostname resolves to a public address, rather than warning — the configuration it prevents is invisible while it is happening, so a log line would not be a defence. If a public address really is right for your deployment (MinIO on its own host, say), set ALLOW_PUBLIC_STORAGE_ENDPOINT=true in backend/.env.

    Three of those are unrecoverable

    Changing PASSWORD_PEPPER invalidates every password hash ever written. Losing ENCRYPTION_KEY loses the encrypted columns. Losing MINIO_KMS_SECRET_KEY loses every uploaded file. Put all three somewhere off the machine before you continue.

  6. Certificates for the internal hops

    shell
    bash scripts/gen-internal-certs.sh ./certs

    Not the public certificate — Caddy gets that from Let's Encrypt on its own. These encrypt the container-to-container hops, which the startup checks require outside development. Rotate with make rotate-internal-certs, and put scripts/check-cert-expiry.sh in cron: nothing renews these, and when they lapse the public certificate is still perfectly healthy, so the obvious suspect is innocent.

  7. Build

    shell

  -e PUBLIC_SITE_URL=https://$APEX \

  -e VITE_API_URL=https://$APP \

    && pnpm build && chown -R $(id -u):$(id -g) /repo"

docker compose -f docker-compose.prod.yml build backend

    In a container so the host needs no Node, and as root inside it because corepack requires that — ownership is handed back at the end. No Python is needed: the generated API client is committed.

    All three variables matter. PUBLIC_SITE_URL must equal PRODUCTION_ORIGIN exactly or the site ships Disallow: /. PUBLIC_APP_URL is every link into the app — Sign in, Register, the pricing CTA — and without it they all point at localhost on a page that otherwise looks perfect. That one shipped for real; a build gate now refuses it.

  8. Migrate, then start

    shell
    C="docker compose -f docker-compose.prod.yml -f docker-compose.tls.yml"

$C up -d postgres pgbouncer redis minio minio-init
$C ps                       # wait for healthy, not merely running

$C logs -f caddy            # watch three certificates be issued

    python -m app.core.migrations, never alembic upgrade head: each optional module branches off the core trunk with its own label, so there is no single head and that command cannot succeed here.

    pgbouncer reporting healthy is the first real signal — its healthcheck opens a genuine pooled connection through to Postgres, so it means TLS on both hops is working.

  9. Point the plans at real Stripe prices

    shell
    $C exec -T backend python -m app.core.sync_plans

    Skip this and billing cannot sell anything. make seed writes development plans whose price ids — price_pro_monthly and friends — are placeholders, not Stripe ids, because a dev machine has no Stripe account to hold real ones.

    The half that fails silently

    A wrong price id breaks billing in both directions. Checkout answers 502, which you will notice. The webhook does not: _handle_subscription_upserted resolves the incoming subscription back to a plan by that same id, and on a miss it logs billing.webhook_unknown_price and returns — leaving a customer who has just paid sitting on the free tier, with nothing in the UI to say so.

    You never type a price id. product/config.py's PLANS names a lookup key for each price — a stable name you set on the price in Stripe (Product → the price → Edit → Advanced → Lookup key) — and this command resolves those to ids and writes them in. Stripe owns the name and the amount; the repo owns the entitlements, which Stripe knows nothing about. Re-run it after any price change, and once per environment: test-mode and live-mode ids differ while the lookup keys do not.

    It resolves everything before writing anything, so a missing lookup key aborts the run naming every key it could not find and leaves the database untouched. Locally the same thing is make sync-plans.

  11. Keep it running

    shell

    Turn on your provider's snapshots. Postgres and MinIO both live in Docker volumes on that disk, so until you have something better, the snapshot is your recovery story. docs/runbooks/backup-restore.md is the something better.

Three placeholders the stack boots with

RESEND_API_KEY is the one that blocks real use: every authentication email goes through the job queue, so without it nobody can complete a signup. An empty VIRUSTOTAL_API_KEY makes uploads fail at the scan step, and placeholder Stripe keys make billing endpoints fail. The app starts with all three — only the first stops you having users.

Updating a running deployment

The first deploy is ten steps. An update is four, and three of them are conditional — the work is deciding which apply, not running them.

shell
cd ~/forge
export APEX=example.com APP=app.example.com   # a fresh SSH session has these empty

git fetch origin
git checkout main          # first time only, if the box was pinned to a branch
git pull --ff-only

# 1. frontend -- only if apps/ or packages/ changed
docker run --rm -v "$PWD":/repo -w /repo   -e PUBLIC_SITE_URL=https://$APEX   -e PUBLIC_APP_URL=https://$APP   -e VITE_API_URL=https://$APP   node:22-slim sh -c "corepack enable && pnpm install --frozen-lockfile     && pnpm build && chown -R $(id -u):$(id -g) /repo"

# 2. backend -- only if backend/ changed
docker compose -f docker-compose.prod.yml build backend

C="docker compose -f docker-compose.prod.yml -f docker-compose.tls.yml"

# 3. migrations -- only if backend/app/**/migrations/ gained a file
$C run --rm backend python -m app.core.migrations

# 4. restart what you rebuilt
$C up -d backend worker caddy

git diff --stat HEAD@{1} after the pull answers all three conditions at once. If only docs/ or .github/ moved, there is nothing to do on the box at all.

Do not reach for --force-recreate

Plain up -d recreates only the containers whose image or configuration actually changed, which is what you want. --force-recreate restarts everything, and a restart is a process kill: any cleanup written in a finally block does not run. Six of those in one afternoon is what leaked the SSE connection counters and made the app answer 429 to every notification stream. Use it only when you have changed something Compose cannot see, and know what you are interrupting.

The environment variables are not optional on a rebuild

PUBLIC_APP_URL and friends are shell variables, not stored anywhere, so a new SSH session starts without them. Rebuilding the frontend with them empty is how every link into the app once shipped pointing at localhost. A build gate refuses that now — the build fails rather than the site lying — but the failure is easier to read if you know why it happened.

Worked example: the free-tier storage change

Useful because it exercises the conditionals rather than all four steps. That change edited backend/ and one comment in apps/web, and added no migration:

shell
cd ~/forge && git checkout main && git pull --ff-only

docker compose -f docker-compose.prod.yml build backend
C="docker compose -f docker-compose.prod.yml -f docker-compose.tls.yml"
$C up -d backend worker

# it is in the image now, not in the database
$C exec -T backend python -c   "from app.modules.billing.dependencies import _FREE_PLAN; print(_FREE_PLAN.features)"

No frontend rebuild (a comment does not change behaviour), no migration, no seed. _FREE_PLAN is a Python object built at import time, so its numbers ship inside the image and take effect when the process restarts — there is no row to update and nothing to run.

Nor is there a cache to wait out, which is worth knowing because the instinct is wrong. Entitlements are cached for sixty seconds, but what gets cached is the org's Subscription and Plan rows. A free org has neither, so the cached payload is two nulls and the resolver falls through to the in-memory _FREE_PLAN every time. The new caps apply on the first request after the restart.

Then confirm it from outside: log in as an org that has never paid and set an avatar. GET /api/v1/files answering 200 instead of 402 is the same signal without the browser.

Going back

git checkout <previous-sha> and repeat whichever of the four steps you ran. Rolling back a migration is the exception — that needs docs/runbooks/, not this list, which is a good reason to deploy schema changes on their own rather than bundled with code.

Deploying to a managed platform

docs/runbooks/deploy-render.md is the worked example. The shape is:

  1. CI builds and pushes an image to the GitHub container registry on every green main.
  2. Create a web service and a background worker from that same image — the worker's start command is arq app.workers.main.WorkerSettings.
  3. Add managed Postgres and Redis.
  4. Point the health check at /health/ready, which verifies dependencies rather than just process liveness.
  5. Set the deployment secrets so CI can trigger a deploy and run migrations.
Before your first real deploy

Walk docs/runbooks/phase4-verification.md. It is the integrated acceptance pass — eleven numbered steps covering the marketing site, SEO, consent, API keys, webhooks, SSO, module toggles, a security re-scan and load. It is written to be run by somebody who did not build the system.

Operator switches that need no deploy

  • Maintenance mode — turns the product read-only with an exemption list, so you can still work while customers cannot write.
  • A global banner — for telling everyone about an incident.
  • Kill switches — disable an expensive subsystem without shipping code.

See docs/adr/0005 for why these live in the database rather than in environment variables.

What CI runs

Thirteen jobs. lint, test and security gate everything else; then build produces the image, and module-matrix, e2e-web, zap-baseline, lighthouse and storybook run against it. Nightly workflows cover load testing, the aggressive security scan and the mobile end-to-end suite.

One job is currently red, on purpose

e2e-web's visual-regression baselines were generated in a local container and do not match the CI runner's rendering. Regenerating them from whatever CI produced would make the job green and the test meaningless, so it is left failing until someone compares the artifacts and decides what the baselines should be.

Traps worth knowing before you hit them

  • Translation placeholders are ICU — {name}, not {{name}}. The double-brace form throws at render time and takes the page down.
  • Generated files are gitignored — the API client, its OpenAPI document and the i18n key types. Regenerate after pulling.
  • The marketing test suite owns dist/ — do not run it alongside anything else that builds the site, or roughly twenty tests fail for no real reason.
  • A test can pass alone and fail in the suite — usually a logging config that disables loggers process-wide, or settings bound at import time before the test environment applies.
  • Never patch httpx.AsyncClient globally in a backend test — the suite's own client is one, so the patch redirects the test's own requests and produces a baffling empty 404.
